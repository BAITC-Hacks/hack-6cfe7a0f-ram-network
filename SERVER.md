# Firebird: аккаунты, письма и заявки

Дополнительно доступен интерфейс RU/Қазақша/EN и отдельный ИИ-помощник. Его сервер, ключ и схема совместной работы через HTTPS-прокси описаны в [assistant/README.md](assistant/README.md). Python-сервис сохраняет свои аккаунты, CAPTCHA и письма; Node-помощник подключается отдельным процессом.

Существующие HTML/CSS/JavaScript продолжают работать как статический каталог. Аккаунты, подписка и настоящие заявки, включая заявки **без регистрации**, работают **только при запуске `server.py` на сервере**. GitHub Pages не запускает Python и не хранит базу: локальное интерактивное демо не отправляет настоящих заявок или писем. Демо-данные не мигрируют на сервер автоматически. Не вводите пароли в публичные файлы и не имитируйте авторизацию через localStorage.

Сайт сохраняет Bento-дизайн. Заявка содержит подрядчика, дату, предварительный бюджет в тенге и пожелания. Это **не оплата и не автоматическая бронь**: текущий каталог анонимизирован/демонстрационный, действительных контактов подрядчиков нет. Заявки поступают оператору сайта, а не вымышленным подрядчикам. Прежде чем принимать реальные заказы, замените каталог проверенными профилями и согласуйте процесс обработки.

## Локальная проверка без внешних сервисов

Требуется Python 3.12+. Из корня проекта:

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
$env:FIREBIRD_DEV = '1'
$env:FIREBIRD_PUBLIC_URL = 'http://127.0.0.1:4173'
.venv\Scripts\python server.py serve
```

Откройте `http://127.0.0.1:4173`. Вторая консоль с теми же переменными:

```powershell
.venv\Scripts\python server.py worker
```

В разработке CAPTCHA **отключена**, наружу письма **не отправляются**, а сервер принимает запросы только с loopback-адреса. Для просмотра доставленных тестовых писем и ссылок подтверждения используйте третью локальную консоль:

```powershell
.venv\Scripts\python server.py inbox
```

Не публикуйте вывод `inbox`: он содержит одноразовые ссылки. Они не возвращаются API и не попадают в серверные логи. Тестовый ящик очищается спустя 7 дней. Пароль: от 12 до 128 символов. Регистрация не подписывает на рассылку автоматически; включить её можно отдельно после подтверждения email.

## Развёртывание для всех пользователей

Нужен один сервер/контейнер с HTTPS-доменом, постоянным локальным диском и двумя процессами: web + worker. Не запускайте SQLite на общем сетевом диске и не масштабируйте контейнеры на независимые диски. Для нескольких машин сначала мигрируйте БД и очередь на подходящую общую инфраструктуру.

1. Настройте домен и HTTPS у хостинга. Перенесите **весь** сайт на один origin с API: например, `https://firebird.example.com/`. Это не отдельный кросс-доменный API для GitHub Pages.
2. Создайте Cloudflare Turnstile-виджет для этого домена. Секретный ключ остаётся только на сервере; публичный site key передаётся фронтенду. Сервер проверяет ответ Cloudflare, hostname и action (`register`, `login`, `forgot`, `reset`, `resend`, `order`, `guest_order`).
3. Подтвердите домен отправителя в Resend, настройте DNS-записи сервиса и создайте API-ключ только для отправки. Используйте действующий адрес отправителя.
4. Внесите переменные из `.env.example` в секретные настройки хостинга. `.env` автоматически **не загружается**. `FIREBIRD_DEV=0`, `FIREBIRD_PUBLIC_URL=https://...`, абсолютный `FIREBIRD_DATABASE` на постоянном диске, оба ключа Turnstile, `RESEND_API_KEY`, `FIREBIRD_MAIL_FROM` обязательны. Без HTTPS/ключей приложение откажется запускаться, а не включит обход безопасности.
5. Установите зависимости; запустите `python server.py serve` и отдельным управляемым процессом `python server.py worker` с тем же каталогом, переменными и диском. Настройте автоматический перезапуск обоих.
6. Направьте HTTPS reverse proxy на порт `4173`, ограничьте доступ к порту извне, задайте лимит тела запроса 16 КБ и лимиты частоты запросов по IP на прокси. Не передавайте непроверенные proxy headers. При одном контролируемом прокси задайте `FIREBIRD_TRUSTED_PROXY` его **точным исходящим IP** (например, `127.0.0.1` для локального nginx): Waitress доверяет `X-Forwarded-For`/`X-Forwarded-Proto` только этому адресу и только одному hop. Прокси должен перезаписывать, а не пропускать клиентские заголовки. `*` запрещён. Если инфраструктура неизвестна, оставьте поле пустым; тогда лимит по IP может быть общим для всех посетителей за прокси, а лимиты email/пользователя продолжают действовать.
7. Проверьте `/healthz`, регистрацию и подтверждение реального письма, вход, сброс пароля, подписку и создание/отмену заявки. Отдельно проверьте гостевую заявку без аккаунта: `awaiting_email` → настоящее письмо → явная кнопка подтверждения → `pending` → действие оператора и письмо со статусом. Health означает доступность приложения/БД, **не успешную доставку почты**. Наблюдайте вывод worker (`sent`, `failed`, `skipped`) и статусы обеих очередей `outbox` и `guest_outbox`.

### Docker

```sh
docker build -t firebird .
docker volume create firebird-data
docker run -d --name firebird-web --restart unless-stopped --env-file .env -v firebird-data:/data -p 127.0.0.1:4173:4173 firebird
docker run -d --name firebird-worker --restart unless-stopped --env-file .env -v firebird-data:/data firebird python server.py worker
```

Для `--env-file` задайте `FIREBIRD_MAIL_FROM=hello@your-domain.example` (без лишних кавычек), настоящий HTTPS origin и `FIREBIRD_BIND=0.0.0.0`. Пример использует локальный reverse proxy для TLS; без него не открывайте сайт для регистрации. При bind mount `/data` вместо Docker volume предоставьте запись пользователю UID 10001.

## Заявки и оператор

Доступны состояния `pending`, `accepted`, `declined`, `cancelled`. Пользователь видит только свои заявки и может отменить ожидающую заявку; принятую/отклонённую оператором изменить через пользовательский API нельзя. При создании проверяются каталог, его календарное окно, занятые даты и уже принятые заявки. Бюджет — целое число от 1 до 1 000 000 000 ₸; пожелания — до 2000 символов. Повторная отправка одного `requestId` не создаёт копию.

### Гостевые заявки без аккаунта

`GET /api/config` объявляет `guestOrders: true`. Гостю нужны имя, email, подрядчик, дата и бюджет; пароль и регистрация не требуются. Сервер хранит их в отдельных таблицах `guest_orders`, `guest_owners`, `guest_tokens` и `guest_outbox`. Записи `users` не создаются, рассылка не включается, существующий аккаунт с таким же email не получает и не теряет доступ.

1. Фронтенд получает анонимную HttpOnly-сессию и CSRF через `GET /api/session`.
2. `POST /api/guest-orders` принимает `{name,email,providerId,date,budget,wishes,requestId,captchaToken}` и возвращает `{order}` со статусом `awaiting_email` (201; точный повтор — 200). `requestId` — UUID, повтор с другим содержимым — 409. Проверяются Origin, CSRF и Turnstile action `guest_order`; не более пяти отправок на email и 15 на IP в час.
3. Одновременно с заявкой в постоянную очередь сохраняется письмо со ссылкой `/?guest=...`. Ссылка содержит случайный одноразовый токен, в таблице токенов хранится только SHA-256. Срок — 24 часа. GET ничего не подтверждает, поэтому почтовый сканер не отправляет заявку в работу.
4. После явного подтверждения посетителем `POST /api/guest-orders/verify {token}` повторно проверяет каталог, календарь и занятые даты, переводит заявку в `pending` и ставит подтверждение в очередь. Заявка не резервирует слот автоматически. Первое подтверждение можно выполнить в другом браузере: этот браузер и браузер создания получают доступ к одной заявке. Повтор после потерянного ответа безопасно возвращает результат только уже владеющей сессии; использованную ссылку нельзя перенести в третий браузер.
5. `GET /api/guest-orders` показывает до 100 последних заявок только текущей сессии. `POST /api/guest-orders/:id/cancel` отменяет свою `awaiting_email` или `pending` заявку; подтверждённому адресу ставится письмо об отмене. Чужой UUID или совпадающий email не дают доступа. Вход и выход из аккаунта меняют cookie и сохраняют гостевые заявки текущего браузера. Сессия действует до семи дней; после очистки cookie, истечения сессии или сброса пароля может потребоваться обращение к оператору с номером заявки. Публичного поиска заявок по email нет.

Worker закрывает неподтверждённые заявки через 24 часа и прекращает их письма. Не отправленные ещё письма подтверждения отменяются при отмене заявки; уже переданное почтовому сервису письмо отозвать нельзя. Тело письма содержит токен до отправки, поэтому очередь и резервные копии требуют такой же защиты, как БД аккаунтов. `guest_outbox` использует те же lease-замки, постоянный idempotency key, максимум семь попыток и окно 23 часа. Worker обрабатывает ограниченную партию из каждой очереди за проход; его существующие счётчики включают гостевые письма.

Команды оператора ниже работают с обеими таблицами; в `orders` есть поле `source` (`account`/`guest`). Статус `awaiting_email` можно отменить, но нельзя принять до подтверждения email. Транзакции и перекрёстные SQL-триггеры исключают принятие гостевой и обычной заявки на один слот одновременно.

Оператор работает локально на сервере (публичного административного API нет):

```sh
python server.py orders
python server.py order-status --id UUID-ЗАЯВКИ --status accepted
python server.py order-status --id UUID-ЗАЯВКИ --status declined
python server.py order-status --id UUID-ЗАЯВКИ --status cancelled
```

Принятие выполняется транзакционно с повторной проверкой доступности и уникальным слотом подрядчик+дата. **Принимайте заявку только после ручного согласования реальных условий с подрядчиком.** Статус в системе не создаёт договор и не принимает оплату. Оператор может отменить ожидающую или принятую заявку после ручного согласования; отменённые/отклонённые заявки не восстанавливаются. Пользователь получает письмо об изменении статуса. Команда `orders` содержит имя, email заказчика и персональные пожелания для ручной связи; ограничьте доступ к серверу. В HTTP API чужие контакты не раскрываются.

## Рассылка и доставка

- Подписка выключена по умолчанию, нужна подтверждённая почта. Включается/выключается в кабинете.
- Первый запуск worker запоминает текущие ID без массовой рассылки. После обновления `catalog.js` только действительно новые ID создают уведомления. Редактирование имени, рестарт и повторное добавление ранее известного ID не создают дубль.
- Письма сохраняются в outbox в той же БД. Worker отправляет их через Resend, использует атомарные lease-замки и постоянный idempotency key. Повторы ограничены 7 попытками и 23 часами, чтобы не выйти за 24-часовое окно дедупликации Resend. После исчерпания попыток требуется проверка оператором; автоматического бесконечного повторения нет.
- Перед доставкой рассылки повторно проверяется подписка. Отписка отменяет ещё не взятые на отправку уведомления; письмо, уже переданное провайдеру, отозвать нельзя.
- В рассылке есть ссылка отписки. GET открывает подтверждение, POST с CSRF отключает подписку: сканеры ссылок не меняют настройки.
- Тела доставленных писем удаляются из outbox. В локальном dev inbox они сохраняются на 7 дней. Завершённые записи outbox удаляются через 30 дней. Ошибки не содержат тела ответа почтового сервиса/секретов.

## Безопасность и обслуживание

Пароли хешируются scrypt. Сессии — случайные отзываемые server-side токены, в БД хранится SHA-256; production cookie `__Host-firebird` имеет HttpOnly, Secure, SameSite=Lax. Вход обновляет cookie и CSRF. Выход отзывает текущую сессию, сброс пароля — все сессии пользователя. Подтверждение email и сброс используют одноразовые хешированные токены со сроком 24 часа и 30 минут. В outbox непереданные письма временно содержат исходную ссылку: защитите диск и резервные копии.

Все изменения проверяют Origin и CSRF; API не разрешает CORS. Публичные файлы перечислены в allowlist: `.env`, БД, исходный Python, ZIP и документация через сервер недоступны. GitHub-репозиторий сам по себе не хранит секретов и пользовательских БД. Сайт должен передаваться по HTTPS. Не включайте access logging query strings: ссылки подтверждения могут содержать токены до удаления фронтендом. Бэкапы БД делайте через SQLite backup API/команду `.backup` с защищённым хранением, а не копированием только основного файла работающей WAL-БД.

Перед реальным запуском настройте политику конфиденциальности, контакт оператора, сроки хранения аккаунтов/заявок и обработку запросов на удаление; эти бизнес-настройки не выдуманы в коде. Ограничьте доступ к БД и регулярно обновляйте зависимости. Это рабочая реализация для одного серверного узла, не замена аудиту безопасности и эксплуатационному мониторингу.

## Тесты

```sh
python -m unittest -v test_server.py test_guest_server.py
```

Тесты используют временную SQLite-БД и явные TESTING overrides, не отправляют внешнюю почту и не обращаются к CAPTCHA. `TODAY`, `CAPTCHA_VERIFY`, `MAIL_SEND` запрещены вне TESTING. Production CAPTCHA никогда не заменяется локальным флажком «я не робот».

Первичные справочники: [проверка Turnstile на сервере](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/), [отправка писем Resend](https://resend.com/docs/api-reference/emails/send-email), [идемпотентность Resend](https://resend.com/docs/dashboard/emails/idempotency-keys), [безопасность Flask](https://flask.palletsprojects.com/en/stable/web-security/).
